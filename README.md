# MediTwin AI

**Intelligent Hospital Digital Twin & Predictive Healthcare Platform**

University Data Science + AI/ML project (educational prototype).

## Disclaimer

All datasets and risk labels in this repository are **synthetic** and created for academic learning only.
MediTwin AI is **not** a clinical decision system and must **not** be used for diagnosis, treatment, triage,
or live hospital operations. It has no connection to real hospitals, sensors, patient records or hospital systems.

## Dataset decision (read this first)

The application, model training, digital twin, What-If simulator and dashboard all use **one** primary source:
the **synthetic daily hospital-operations dataset** generated by `src/data/generate_synthetic_data.py`
(366 days, seed 42), plus the **synthetic patient dataset** (1,000 records) for patient-risk classification.

The four CSVs from the project's first report (`patients.csv`, `services_weekly.csv`, `staff.csv`, `staff_schedule.csv`; weekly,
per-service) have a different time granularity and structure. They are **not** merged into this pipeline and the application
does **not** use them. Consequently there is no per-service view and no "refused requests" figure.
See [docs/DATA_DICTIONARY.md](docs/DATA_DICTIONARY.md).

## What is real, predicted and rule-based

| Label in the app | Meaning |
|---|---|
| **Recorded** (was "Observed") | a value stored in the synthetic dataset |
| **Expected** (was "ML-predicted") | output of a trained model: OPD forecast, waiting time, patient-risk class, unusual-activity flag |
| **Estimated** (was "Rule-derived") | a formula or heuristic: beds, ICU, emergency cases, medicine stock/consumption and staff workload in the twin and What-If, all recommendations |

Model names, metrics and limitations are kept in the **How this is calculated** sections of the app. No trained model exists for bed, ICU, medicine or staffing demand. Details and measured performance: [docs/MODEL_CARDS.md](docs/MODEL_CARDS.md).

## Run order (from the project root)

```bash
python -m src.data.generate_synthetic_data     # synthetic CSVs + injected-spike ground truth
python -m src.data.preprocess                  # cleaned CSVs
python -m src.features.feature_engineering     # feature CSVs
python -m src.models.train_all                 # train all four models and write the comparison
streamlit run app.py                           # dashboard at http://localhost:8501
python -m unittest discover -s tests -t .      # full test suite
```

`python -m src.models.train_all --skip patient_risk` keeps the existing patient-risk model.
Generating data again with the same seed reproduces the saved CSVs exactly. Prophet is an *optional* forecasting candidate: if its Stan backend
cannot run on your machine it is recorded as skipped and the other candidates still train.

## Dashboard design

**Medical Sage**, a light theme used on the landing page and the dashboard: deep sage `#145A55`, teal `#2E7D73`, soft sage `#88BFA3`, page background `#F2F7F5`, white surfaces,
warm neutral `#E8E2D6`, text `#142B2A` (amber and red are reserved for warnings, and severity also uses a shape and a word; text colours are tested for WCAG AA contrast).
Typography is Inter, self-hosted in `static/` (no external font request); page titles 26 px, body 13.5 to 14 px, KPI values 27 to 28 px.
Navigation is a slim floating **rail** on the left (CSS only): compact it shows icons, hovering it or moving keyboard focus into it reveals the labels without moving the page, and **Keep menu open** pins it expanded. Pages are grouped **Today** (Overview, Alerts, Trends), **Look ahead** (Forecasts, Patient Risk) and **Plan** (Hospital Twin, What-If); the bottom of the rail has the synthetic-data indicator, the Plain-language guide, the pin toggle and Sign out. On phones Streamlit's own drawer is used.
The Overview leads with a status band (bed and ICU capacity rings) and a KPI strip with real 30-day trend lines.
Screenshots of every page are in [docs/screenshots/](docs/screenshots/) and a presenter script is in [docs/DEMO_WALKTHROUGH.md](docs/DEMO_WALKTHROUGH.md).
Designed for desktop and laptop widths (1280 to 1920 px); tablets stack the layout; **phones are a basic fallback only** (the landing page and sign-in stack cleanly).

## Product journey and demo access

`streamlit run app.py` opens the public **landing page** (`/`). **Get Started** or **Sign in** leads to `/signin`, where you can create a demo account, sign in, or **Continue as demo user**
(no password needed). The dashboard lives at `/workspace` and is only shown to a signed-in session; **Sign out** in the sidebar ends the session.

**This is demonstration access, not production authentication.** Accounts exist only in the running server's memory (nothing is stored on disk) and last for one browser session;
passwords are hashed with PBKDF2 but there is no rate limiting, e-mail verification, password reset or encrypted transport, and the gate can be bypassed by anyone who can edit the code.
Do not enter a real password. A production system would use an identity provider (for example Streamlit `st.login` with OIDC). Details: `src/ui/auth.py` and [docs/RELEASE_NOTES.md](docs/RELEASE_NOTES.md).

## Alerts

Eight categories: bed occupancy, ICU pressure, high OPD load, **rising OPD demand**, low medicine stock (days of cover), high medicine consumption,
staff workload, and unusual activity (Isolation Forest). Four severities (Low/Medium/High/Critical) from configurable ladders in `AlertThresholds`
(`src/alerts/models.py`); illustrative, not clinical. One alert per category, scope and date. Every category can be raised from the What-If controls;
rising demand compares the scenario with its baseline day and is labelled rule-derived (an ML forecast is used only for the real predicted state).
On the untouched latest day only a low "rising OPD" alert is present; pressure appears in the documented periods of the data and in scenarios.

## What-If simulator

Waiting time is the only value scored by a model; baseline and scenario use the same model and inputs, so "no change" shows exactly zero difference.
Other values are rules: demand scales with an OPD + emergency volume ratio, ICU demand adds 0.17 per extra emergency and 0.045 per extra occupied bed
(the generator's coefficients), medicine use is `0.8*OPD + 2.5*emergency + 1.2*admissions`. The medicine-stock control scales the stock on hand
at the start of the day (for example -60% for a delayed delivery) and adds "medicine stock" and "days of cover" rows. The waiting-time model has no ICU-capacity
input, so ICU capacity does not change waiting time. Out-of-range or invalid scenarios raise `ScenarioError`.

```python
from src.simulation.what_if import WhatIfSimulator
from src.twin.hospital_twin import build_twin_from_latest

twin = build_twin_from_latest()
result = WhatIfSimulator().simulate(twin.get_current_state(), patient_inflow_percent=20, medicine_stock_percent=-60)
print(result.summary_text())
```

## Digital twin

`HospitalDigitalTwin` holds the latest dataset day and predicts 1 to 7 days ahead. Only the OPD count (forecaster) and the waiting time (regressor) are ML-predicted.
Beds (2% of the OPD change), ICU (15% of the emergency change), emergency cases (weekend uplift), and medicine stock (drawdown only) are heuristics, so they stay close
to today's values; doctors and nurses are carried forward. `model_waiting_time()` scores today's inputs with the same model and feature builder as future days, so
the twin's comparison is like for like (the observed value is shown separately).
Provenance is declared in `CURRENT_FIELD_SOURCES` / `PREDICTED_FIELD_SOURCES` and tested against the UI labels.

## Known limitations

* **All data is synthetic**; scores measure how well models learn the generator, not real-world accuracy. Patient-risk labels are a deterministic rule.
* OPD forecasting: the selected trained model is not clearly better than a day-of-week average on the 30-day test block; Prophet could not be evaluated on the development machine.
  The forecast band is an empirical range (70% test coverage), not a validated 80% interval.
* Patient-risk High-class recall is 54%; the page is an educational demonstration and must not be read as a diagnosis.
* Resource projections (beds, ICU, medicine, staffing) are rules/heuristics, not trained models; `equipment_availability_percentage` is unused.
* The anomaly evaluation rests on four injected spikes; contamination was tuned on them.
* Sign-in is demonstration access only (in-memory accounts, one browser session, no production security); see "Product journey and demo access".
* No per-service view, no refused-request data, no live updating, database or API. The layout targets desktop/laptop widths; phone layout is basic (the navigation drawer overlays content).
* Resolved in this version: the generator's occupancy floor/warm-up drift, the near-constant medicine stock, the Prophet forecast that scored worse than a mean baseline,
  and the observed-vs-predicted waiting-time comparison in the twin and overview.

## Synthetic risk labelling

Patient `risk_level` comes from transparent rule-based scoring (age, vitals, chronic disease, emergency flag, previous admissions;
`risk_score_breakdown` itemises it). The rules are simplified for teaching and are **not** medical guidelines.
